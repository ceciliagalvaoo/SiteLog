# ADR-0001: Persistence model and migration strategy

- **Status:** Accepted
- **Date:** 2026-10-31
- **Milestone:** M1

## Context

SiteLog stores daily logs that become legal records after sign-off, safety incidents with a
severity workflow, and an aggregated compliance report. The assignment requires:

- PostgreSQL or MySQL for the graded version, schema and seed data from Flyway or Liquibase,
  no schema generated by Hibernate (`ddl-auto` must be `validate` or `none`);
- a managed free database for the deployed instance;
- Spring Data JPA on Hibernate 7 with at least one one-to-many, one many-to-many **with an
  association entity carrying attributes**, and one optional relation;
- a conscious choice between lazy and eager loading, and one N+1 problem found and fixed.

Two domain constraints shape the model:

1. A signed-off daily log must not change, and two users editing the same log or incident
   at the same time must not silently overwrite each other.
2. A crew's work on a work entry has its own data (hours worked, worker count, task), so the
   `WorkEntry`–`Crew` link is more than a pair of keys.

The entities and relations are described in the [domain model](../architecture/domain-model.md).

## Decision

1. **PostgreSQL everywhere it matters.** PostgreSQL 17 in `docker-compose` for local
   development and in Testcontainers for integration tests; Supabase (managed PostgreSQL)
   in production. No H2.
2. **Flyway owns the schema.** Versioned SQL migrations in `src/main/resources/db/migration`
   (`V1__baseline.sql`, then one migration per change). Seed data in its own migration.
   Hibernate runs with `spring.jpa.hibernate.ddl-auto=validate`, so a mismatch between the
   entities and the migrations fails at startup. A committed migration is never edited; a
   fix is a new migration.
3. **Aggregate boundaries.** `DailyLog` is the root of `WorkEntry` and `CrewAssignment`
   (`cascade = ALL`, `orphanRemoval = true`); `Incident` is the root of `CorrectiveAction`.
   `Site`, `Crew` and `AppUser` are referenced, never cascaded. Deleting a site with logs or
   incidents is refused by the foreign keys (`ON DELETE RESTRICT`), because logs are records,
   not disposable children.
4. **`CrewAssignment` is an entity.** It has a surrogate `id`, `@ManyToOne` to `WorkEntry`
   and to `Crew`, the attributes `hoursWorked`, `workerCount`, `task`, and a unique
   constraint on `(work_entry_id, crew_id)`. `Incident` ↔ `Crew` (affected crews) has no
   attributes and stays a plain `@ManyToMany`.
5. **`LAZY` by default, including `@ManyToOne` and `@OneToOne`.** Each screen or endpoint
   that needs related data loads it explicitly with a JPQL fetch join or `@EntityGraph` on
   the repository method. `spring.jpa.open-in-view=false`, so lazy loading outside a
   transaction fails visibly instead of issuing hidden queries from the view.
6. **Optimistic locking with `@Version`** on the two aggregate roots, `DailyLog` and
   `Incident`. A stale write raises `ObjectOptimisticLockingFailureException`, mapped to
   **409 Conflict** (`ProblemDetail` in the API, flash message on screens). Hibernate does
   **not** increment the root's version when only a child row changes (a `WorkEntry` or
   `CrewAssignment` update touches only the child table). Therefore every service method that
   adds, changes or removes a child loads the root with
   `LockModeType.OPTIMISTIC_FORCE_INCREMENT` (or bumps the root's version explicitly), so two
   concurrent edits of the same log, even on different children, conflict on
   `daily_log.version` and the second one gets 409. The same rule applies to `Incident` and
   `CorrectiveAction`.
7. **Production database: Supabase.** The Render service connects through the Supavisor
   pooler in **session mode** with `sslmode=require` (the direct connection is IPv6-only;
   session mode keeps one server connection per client connection, which is compatible with
   the PostgreSQL JDBC driver's prepared statements). Flyway runs on application startup
   against the same database. Credentials come only from environment variables.

## Alternatives rejected and why

| Alternative | Why rejected |
|---|---|
| **H2 (in-memory) for development or tests** | Different SQL dialect and behaviour (triggers, `timestamptz`, constraint errors). The log-locking guarantee will rely on a PostgreSQL trigger, which H2 cannot run. The assignment also deducts points for H2 in the graded version. Testcontainers gives a real PostgreSQL in tests at the cost of a few seconds. |
| **`ddl-auto=update` / `create`** | Schema changes become implicit and unreviewable, there is no history, and it cannot create triggers or partial indexes. Deducted by the assignment. |
| **Liquibase** | Same capability for this project, but changelogs in XML/YAML add an abstraction over SQL. Plain SQL migrations are easier to review and to explain, and PostgreSQL-specific features (triggers, `EXPLAIN`-driven indexes) are written directly. The migrations are the exact SQL that runs, so each one can be read line by line in a review or at the defence, and the immutability triggers (PL/pgSQL) need raw SQL anyway — in Liquibase they would end up in `<sql>` blocks, losing the benefit of the abstraction. Database portability, Liquibase's main advantage, is not a goal: the project targets PostgreSQL only. |
| **MySQL** | Allowed, but Supabase (chosen host) is PostgreSQL, and PostgreSQL triggers and `EXPLAIN ANALYZE` output are what the locking and performance work will use. |
| **`@ManyToMany` between `WorkEntry` and `Crew`** | A join table managed by `@ManyToMany` cannot hold `hoursWorked`, `workerCount`, `task`. |
| **Composite key (`@EmbeddedId` / `@IdClass`) for `CrewAssignment`** | Works, but needs an embeddable key class with `equals`/`hashCode`, `@MapsId`, and makes REST URLs and form binding clumsier. A surrogate `id` plus `UNIQUE (work_entry_id, crew_id)` gives the same integrity: the database still rejects the same crew twice on one work entry. The surrogate key keeps `equals`/`hashCode` simple, gives each assignment a stable identifier for REST (`/crew-assignments/{id}`) and for the nested form rows, and lets a row change its crew without changing its identity. |
| **`EAGER` fetching (or the JPA default for `@ManyToOne`)** | Loads associations on every query even when unused and causes N+1 queries in lists (each log loads its site, each assignment its crew). Explicit fetch joins make the cost visible per use case. |
| **Pessimistic locking (`SELECT … FOR UPDATE`)** | Holds database locks while a user edits a form, and does not fit a web form workflow spread across requests. Conflicts are rare (one manager per site), so detecting them with `@Version` is enough. |
| **Neon or Render PostgreSQL in production** | Render's free PostgreSQL expires after 30 days, which does not survive from M3 to a defence in January/February. Neon would also work; Supabase was preferred for its built-in SQL editor and table viewer (useful to show the audit tables and trigger effects during the demo), its connection pooler (Supavisor, session mode — reachable over IPv4 from Render), and a free tier without an expiry date. The accepted cost is that an idle free project pauses (see Consequences). |

## Consequences accepted

- **Two places to keep in sync.** Every entity change needs a migration; `validate` catches
  drift at startup, and the integration test (Testcontainers) catches it in CI.
- **More repository code.** Each screen that needs children has a dedicated query with a
  fetch join or entity graph. Forgetting one shows up as a `LazyInitializationException`
  (open-in-view is off) or as extra queries; the N+1 on the daily log list is documented in
  `docs/performance.md` (milestone M4).
- **Conflicts reach the user.** With optimistic locking, the second of two concurrent saves
  fails with 409 and the user must reload. This is intended: a silent overwrite of a log
  that is about to become a legal record is worse.
- **Local and production must match.** Docker, Testcontainers and the Supabase project all run
  PostgreSQL 17 (Supabase: 17.11; local images: `postgres:17-alpine`), so triggers, query plans and migrations behave the same in tests and in
  production.
- **Free tier limits.** The Supabase free project pauses when idle; it has to be resumed
  before demos and the defence (noted in the README). The pooler adds a network hop, and
  the HikariCP pool size has to stay within the pooler's client limit (justified in the
  README with the Hikari configuration).
- **One extra UPDATE per child change.** `OPTIMISTIC_FORCE_INCREMENT` issues
  `UPDATE daily_log SET version = version + 1 WHERE id = ? AND version = ?` (or the same on
  `incident`) at flush, even when the root's own fields did not change. This is the cost of
  detecting concurrent child edits on the root; a service method that forgets the lock mode
  loses that protection, so the concurrency test (M4) covers a child edit.
- **Immutability after sign-off needs more than this ADR.** `@Version` prevents lost updates
  but not edits to a signed-off log; that is enforced by the service and by database triggers
  (advanced requirement 1, milestone M2). The triggers cover `daily_log` **and** its children:
  `INSERT`, `UPDATE` and `DELETE` on `work_entry` and `crew_assignment` are rejected when the
  parent `daily_log.status` is `SIGNED_OFF` (the trigger looks up the parent log through
  `daily_log_id`, or through `work_entry_id` → `daily_log_id` for assignments), and allowed
  when it is `DRAFT` or `REOPENED`. Protecting only the `daily_log` row would leave the
  signed-off content editable through its children.
